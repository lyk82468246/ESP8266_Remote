# 开发与发布流程

1. 先检查 `git status --short`、当前分支和远端，阅读根入口及本次任务相关规则；保留已有用户改动。空仓库先确认远端是否有历史，不能直接覆盖。
2. 明确协议、板级配置和实物证据的边界。能从源码与会话确认的常规选择直接推进；缺失的硬件信息记录为假设，并完成不依赖该信息的工作。
3. 修改相关层，保持入口精简、职责清晰。新功能同步 README、配置样例和对应验证约定。依赖版本固定，升级需有具体原因与兼容验证。
4. 按 [验证规则](../rules/testing.md) 执行必要检查，修复失败；结果记录实际执行范围。不要重复已经通过且未受后续改动影响的测试。
5. 提交前查看 diff 与所有待提交文件，执行 `git diff --check`；新文件需先暂存，再执行 `git diff --cached --check`。用 `git check-ignore` 检查缓存和生成文件应被忽略，`.agents/`、源码、WiFiConfig.h 及脱敏文档应被保留。
6. 提交完整且可审阅的源码、工具、配置和文档。用户指定的项目 WiFi 参数随 WiFiConfig.h 版本管理；其他未经授权的私密信息、构建产物、下载依赖和原始私密证据不进入 Git。“全部推送”指全部应版本管理的成果。
7. 用户已明确要求“每次修改完成后提交并推送，以后都是”。因此每轮完成修改和必要验证后，自动 commit 并推送指定远端或现有 origin，无需再次确认；用户明确要求暂不提交/推送时服从该次指令。推送前确认目标分支和远端历史；禁止强推或丢弃已有提交，正常合并/变基后重新验证受影响部分。验证失败或工作未完成时不要把失败草稿当成完成结果推送。
8. 结束时报告具体变化、验证范围、提交与推送结果；真板未测试则明确说明。不要把构建成功写成已烧录或已联调。

新建任务分支默认使用 `codex/` 前缀；用户指定的分支优先。已有分支按用户任务继续，不为单次整理擅自改变分支策略。硬件烧录和实际输出控制以当前会话授权范围为准。
